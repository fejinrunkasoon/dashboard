# 多媒体广告数据接入与账户权限体系整改方案 V2

版本：V2.0  
适用范围：Meta Ads / Google Ads / TikTok Ads / Snapchat Ads，后续可扩展其他媒体  
核心场景：广告数据 Read-only 接入、Dashboard、账户管理、AI 分析  
整改目标：从当前“Connector 配置驱动”模式，升级为“多租户、多平台、多授权、多账户、可追溯、可授权”的媒体数据基础设施。

---

## 1. 本次整改要解决什么

当前系统已经存在：

```text
Media Platform
Connector
Asset Type
Credential
DEMAND
ACCOUNT_MAP
媒体同步
账户中心
Team
User
日志
```

底层已经有一定平台抽象，但当前最大问题是：

```text
平台怎么接
客户怎么授权
发现了哪些账户
哪些账户正式进入系统
账户属于谁
哪些用户能看到
数据通过哪个授权同步
```

这些不同职责被混合在了一起。

最终系统应该回答下面所有问题：

```text
1. 系统支持哪些媒体平台？

2. 当前 Organization/Team 连接了哪些平台？

3. Meta 是否可以连接多次？
   → 可以

4. 一次 Meta OAuth 是否可以发现多个广告账户？
   → 可以

5. 同一个广告账户能否被多个 OAuth Connection 发现？
   → 可以

6. 这个账户是谁接入系统的？
   → 可追踪

7. 当前通过哪个 Credential 同步？
   → 可追踪

8. 这个账户属于哪个客户？
   → 可追踪

9. 目前由哪个 Team 管理？
   → 可追踪

10. Team Manager 能看到什么？
    → Team 全部账户

11. Team Member 能看到什么？
    → 自己接入 + 被分配的账户

12. Dashboard 能看到什么？
    → 当前用户有权限的账户

13. AI 能分析什么？
    → 当前用户有权限的数据

14. 谁执行了授权/分配/断开/重新授权？
    → Audit Log 可追踪
```

这就是整改后的系统边界。

# 2. 核心设计原则

整个整改按照 8 个原则执行。

## 原则 1：平台能力和客户接入必须分离

现有：

```text
数据接入
→ Connector
→ Credential
→ Asset Type
→ Field
```

实际上混合了两层东西。

整改为：

```text
Control Plane
平台能力配置

Tenant Plane
客户实际数据接入
```

Control Plane 解决：

```text
系统“会不会接 Meta”
```

Tenant Plane 解决：

```text
Nike 的 Team A “有没有接 Meta”
```

两者绝对不能混淆。

---

# 3. 原则 2：Platform ≠ Connection ≠ Account

这是整个系统最重要的领域模型。

```text
Platform
    │
    │ 1:N
    ↓
Connection
    │
    │ N:N
    ↓
Media Account
```

Platform：

```text
META
GOOGLE
TIKTOK
SNAPCHAT
```

代表系统支持的平台。

Connection：

```text
某个用户代表某个组织/团队
完成的一次平台授权
```

例如：

```text
Meta - 王五
Meta - Agency
Google - US MCC
TikTok - 张三
```

Media Account：

```text
真正的广告账户
```

例如：

```text
Meta Ad Account 123456
Google Customer 123-456-7890
TikTok Advertiser 987654
```

三者不允许合并为一个概念。

---

# 4. 原则 3：Connection 是授权渠道，不是业务资产

例如：

```text
王五
↓ OAuth
Meta Connection C001
↓
Meta Account A
```

未来王五离职：

```text
C001 → REVOKED
```

后来张三 OAuth：

```text
C002
↓
Meta Account A
```

Account A：

```text
ID
Campaign
历史 Metrics
Dashboard
AI Context
```

不能因此改变。

因此：

```text
Connection
= 数据访问通道

Media Account
= 企业业务资产
```

必须解耦。

---

# 5. 原则 4：OAuth 权限与系统用户权限严格分离

整个权限模型分三层：

```text
Layer 1
Provider Authorization

Meta / Google / TikTok
决定 Connection 能读取什么。


Layer 2
Tenant Ownership

你的系统
决定数据属于哪个 Organization。


Layer 3
Application Authorization

你的系统
决定 Team / User 能看到什么。
```

OAuth 不能代替 RBAC。

RBAC 也不能扩大 OAuth 的 Provider 权限。

最终权限实际是：

```text
最终可访问数据

=
Provider允许读取
∩
Organization拥有
∩
User有权访问
```

---

# 6. 原则 5：Organization 是强数据边界

推荐：

```text
Organization
= Tenant
```

核心业务数据必须归属于 Organization。

例如：

```text
Connection
Media Account
Campaign
Ad Group
Ad
Metrics
```

都必须能够沿关系追溯到：

```text
organization_id
```

禁止：

```text
Organization A
```

通过 API、Dashboard、Export、AI 获取：

```text
Organization B
```

的数据。

这是最高优先级的数据隔离规则。

---

# 7. 原则 6：Team 是管理边界，User Assignment 是访问边界

不要简单：

```text
Account.user_id
```

应该：

```text
Organization
   ↓
Team
   ↓
Account

User
   ↓
Account Assignment
```

一个 Account 可以：

```text
属于 Team A 管理
```

同时被：

```text
王五
李四
张三
```

共同访问。

---

# 8. 原则 7：所有数据使用必须经过统一权限层

以下全部禁止自己写一套权限：

```text
账户中心
Dashboard
Analytics
Export
Reporting API
AI
```

统一经过：

```text
Account Access Service
```

例如：

```text
getAccessibleAccountIds(user)
```

所有业务模块都使用它。

尤其：

```text
AI
```

不允许直接查询全库。

---

# 9. 原则 8：Provider Raw Data 与业务数据分离

Meta 给你的东西是：

```text
Meta Data
```

你的：

```text
Team
Member
Product
Channel
Fee Policy
Account Manager
```

不是 Meta 数据。

因此必须区分：

```text
Provider Data
Business Metadata
Derived Data
```

避免未来平台同步覆盖内部业务数据。

# 16. “OAuth 成功”和“账户接入成功”不是一个状态

需要明确区分：

```text

```

只是：

```text

```

之后还需要：

```text
Discover
Select
Import
Sync
```

所以不能 OAuth Callback 后直接告诉用户：

```text

```

应该：

```text

请选择需要接入系统的账户。
```

# 18. Connection 与 Account 必须 N:N

增加：

```text
connection_accounts
```

不能只：

```text
media_account.connection_id
```

因为：

```text
Connection A ─┐
              ├→ Account 123
Connection B ─┘
```

完全可能发生。

建议：

```text
connection_accounts

id
organization_id

connection_id
media_account_id

provider_access_status

sync_enabled
is_primary_sync_source

discovered_at
last_verified_at

created_at
updated_at
```

# 19. Media Account 唯一性

Account 身份不能依赖 Connection。

建议逻辑唯一键：

```text

+
platform
+
external_account_id
```

例如：

```text

123456789
```

代表企业内唯一 Media Account。

Connection A 第二次发现它：

```text
不要再次 CREATE Account
```

而是：

```text

```

# 21. Team 与 Account 关系

不要把一个动态管理关系完全写死在 OAuth Connection 上。

建议：

```text

```

这代表：

```text

```

如果业务明确规定一个账户只能属于一个团队，可以在应用层/数据库约束成单 Team。

```text
Team A
Team B
```

# 23. 用户接入账户后的默认行为

假设：

```text
王五
Team A Member
```

接入：

```text
Meta A
Meta B
```

系统自动：

```text
team_accounts

A → Team A
B → Team A
```

同时：

```text
account_assignments

A → 王五 → IMPORTED_BY
B → 王五 → IMPORTED_BY
```

因此王五立即能看到自己的账户。

Team Manager 不需要额外 Assignment。

因为：

```text
Team Manager
→ Team Accounts
```

自动拥有访问权。

# 24. 正式权限矩阵

第一版建议保持简单。

```text
Organization Admin
→ Organization 所有 Account

Team Manager
→ 所管理 Team 的所有 Account

Team Member
→ 自己接入的 Account
  +
  被 Assignment 分配的 Account
```

如果用户同时属于多个 Team，则将可访问范围求 Union。

平台 Connection 的管理权限应另外判断，不要因为用户能看 Account，就默认允许他重授权/断开别人的 Connection。

# 25. 建立统一 Account Access Service

这是本次整改技术上最重要的部分之一。

禁止：

```text
AccountController 自己判断
DashboardService 自己判断
AIService 自己判断
ExportService 自己判断
```

统一：

```text
AccountAccessService
```

提供类似：

```text
getAccessibleAccountIds(userId)

canViewAccount(userId, accountId)

canManageAccount(userId, accountId)

canAssignAccount(userId, accountId)

canManageConnection(userId, connectionId)
```

以后所有业务模块调用这一层。


```text

成员
户管
费率政策

```

来源：

```text
你的业务数据库
```


# 30. Connection 权限不能与 Account 权限混用

这是一个容易忽视的安全问题。

例如：

```text
王五 OAuth
→ Meta Connection
→ Account A
```

主管把：

```text
Account A
```

分给李四。

李四应该能：

```text
查看 Account A
查看 Account A Dashboard
使用 AI 分析 Account A
```

但不意味着李四可以：

```text
查看王五 Token
断开王五 Connection
重新授权王五身份
```

因此：

```text
Account Permission
```

与：

```text
Connection Permission
```

必须独立。

# 31. Credential 整改

你当前 Mock Credential 应退出生产用户流程。

状态从：

```text
DRAFT
MOCK_CONNECTED
EXPIRED
REVOKED
```

逐渐升级为 Connection 状态。

建议：

```text
PENDING_AUTH
ACTIVE
REAUTH_REQUIRED
EXPIRED
REVOKED
DISCONNECTED
ERROR
```

开发环境可以继续：

```text
MOCK
```

但 UI 明确标识：

```text
TEST ONLY
```

并禁止进入生产真实数据链。

# 32. Account 状态与 Connection 状态分开

禁止只有一个：

```text
ACTIVE
```

状态描述所有东西。

至少区分：

```text
Connection Status

ACTIVE
REAUTH_REQUIRED
REVOKED
...
```

与：

```text
Provider Account Status

ACTIVE
DISABLED
SUSPENDED
CLOSED
UNKNOWN
```

以及：

```text
Internal Account Status

ACTIVE
ARCHIVED
DISABLED
```

这样你现在截图里的：

```text
资产状态
媒体状态
```

才真正拥有清晰语义。

# 33. 同步架构整改

数据流：

```text

     ↓
Connection
     ↓
Media Account
     ↓
Sync Job
     ↓
Raw Provider Data
     ↓
Normalizer
     ↓
Unified Ads Model
     ↓
Analytics
     ↓
Dashboard / AI
```

不要：

```text
Dashboard

```

Dashboard 应主要查询你自己的数据库/仓库。

# 34. 同步源选择

由于：

```text
一个 Account
```

可能存在：

```text
多个 Connection
```

因此需要 Primary Sync Source。

例如：

```text
Account A

Connection 1   ACTIVE     PRIMARY
Connection 2   ACTIVE
```

如果 Primary：

```text
REAUTH_REQUIRED
```

后续可以支持：

```text
Connection 2
```

作为替代访问通道。

第一版不必自动切换，可以：

```text
标记异常
→ 管理员手工切换
```

后续再做自动 failover。

# 54. 最终产品方法论

以后整个系统可以始终用六个问题判断一个设计是否合理：

```text
WHO
谁在操作？
→ User


FOR WHOM
代表谁操作？
→ Organization / Team


THROUGH WHAT
通过什么获得媒体访问能力？
→ Connection


WHAT ASSET
获取的是哪个业务资产？
→ Media Account


WHO CAN ACCESS
谁有权使用这个资产？
→ Team + Assignment + RBAC


WHERE DID DATA COME FROM
数据是怎么来的？
→ Platform + Connection + Sync + External ID
```

任何新功能——包括 Snapchat、Pinterest、Amazon Ads、Microsoft Ads、LinkedIn Ads——都先回答这六个问题，再开始开发。

# 55. 最终系统边界

整改完成以后，系统应该形成非常稳定的五层：

```text
① Provider Layer
Meta / Google / TikTok / Snapchat

        ↓

② Integration Layer
Connector / OAuth / Connection / Secret

        ↓

③ Asset Layer
Media Account / Campaign / AdGroup / Ad

        ↓

④ Governance Layer
Organization / Team / Assignment
RBAC / Audit / Access Control

        ↓

⑤ Application Layer
Account Center
Dashboard
Reporting
Export
AI
```

其中最重要的架构纪律是：

```text
Provider Layer
不知道你的 Team。

Connector Layer
不决定谁能看 Dashboard。

Account 本身
不等于 OAuth Connection。

Team Assignment
不拥有 Token。

Dashboard
不直接请求 Provider。

AI
不绕过 Account Authorization。

OAuth User
不等于 Account Owner。
```

这几条一旦守住，未来增加平台、团队、账号数量和 AI 能力时，系统不会越来越乱。

你目前已有的 Connector、Asset Type、Mock Credential、ACCOUNT_MAP 等工作也不需要全部废弃。应该把它们“下沉”为 Platform/Connector Control Plane；然后在其上建立新的 `Connection → ConnectionAccount → MediaAccount → Team/Assignment → Data` 主链。这样属于架构分层整改，而不是推倒重来。
