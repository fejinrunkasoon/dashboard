# FFJ 需求对照（评估稿）

吸收说明：本文「TG Bot 自动下户工作流」已写入 [plan.md](plan.md) §14 / §41。
模拟实现 = STEP 18（[phase_18.md](phase_18.md)）；真实 Bot = STEP 29。
不采用本文旧「TG 群组 / 关键词」设计。与 plan §41 冲突时以 plan 为准。

一、评估结论

整体判断：账户中心已经可以作为 FFJ 工作台的主体方案，不建议按照《FFJ 的工作台》原型重新建设一套独立系统。

FFJ 工作台中的核心“账户运营链路”已经被当前方案较好覆盖：

渠道/产品 → 账户进入账户池 → 团队申请 → 系统推荐/人工分配 → 使用账户 → 消耗监控 → 异常预警 → 转移/回收 → 更换产品/户管 → 数据分析。

另外，账户中心已经存在“登记打款”，因此此前认为渠道打款缺失的判断需要修正。当前主要 Gap 已经从“基础账户管理和打款”转变为“FFJ 特有的数据治理、评分/分析、自动对账、外部数据同步和 Telegram 自动化”等能力。

建议覆盖状态定义：

- ✅ 满足：现方案已有对应能力，可直接承接 FFJ。
- 🟢 更完善：不仅满足 FFJ，而且现方案能力更完整。
- 🟡 部分满足：基础能力存在，但 FFJ 要求的字段、规则、统计视图或流程还需补充。
- 🔴 未看到/需新增：目前材料中没有发现明确对应能力。
- ⚪ 待确认：截图不足以判断，不建议直接作为新增需求。


二、运营总览

FFJ 需求包括：

核心账户指标、账户可用率、异常账户、待处理事项、渠道消耗分析、平台筛选、时间筛选等。

账户中心现状：

已有 Dashboard，并且提供账户数量、使用状态、异常情况、平均生命周期、Spend、趋势图、渠道/团队等多个统计维度。

结论：🟢 更完善。

无需按照 FFJ 首页重新开发。

建议只核对 FFJ 所要求的 KPI 口径，然后把必须指标加入现有 Dashboard。


三、渠道打款

FFJ 包含：

打款录入、打款明细、渠道余额情况、代理 USDT 地址。

账户中心已经存在“登记打款”功能，当前确认字段包括：

- 渠道
- 打款地址
- 业务归属
- 打款金额 USD
- 备注
- 系统自动生成录入日期
- 确认录入
- 录入后进入打款明细

结论：✅ 核心功能满足。

这一点修正上一版分析，不应再列为主要缺失项。

FFJ 另外展示了“渠道余额概览”，包括打款额、累计消耗、剩余余额、预计剩余天数等。如果账户中心已有对应 Finance/Balance 计算，则可判定整个模块完全满足。

“代理 USDT 地址”如果当前的打款地址下拉来源于统一的渠道地址库，那么也已经具备数据基础。

待确认：

USDT 地址是否可以新增、编辑、停用，以及一个渠道是否支持多个地址。

如果支持，则 FFJ 的渠道打款模块基本无需新增。


四、账户与消耗——账户明细

FFJ：

提供 Meta / Google / TikTok 等账户的统一列表，并支持渠道、团队、状态、时间、时区（GMT+/GMT-）等筛选。注意现在系统中的时区语义是没有对其的正确应该是GMT+8/GMT-8这样来表达，而不是直接写地区名字
而且账户字段中，还差账户的 闲置时间 作为判断
账户中心：

已有完整账户中心列表，并采用“常用条件 + 高级筛选”设计。

同时支持账户详情页。

结论：🟢 更完善。

现有高级筛选方案优于在页面顶部持续堆积大量筛选条件，不建议为了匹配 FFJ 原型而修改。


五、账户详情

FFJ 的账户数据实际上散落在多个页面中。

账户中心已经形成统一 Account Detail，包含：

Overview、Spend、Assignment、Product、Status、Profile 等信息，并能够从账户头像直接进入详情。

结论：🟢 更完善。

建议以后所有 FFJ 的“查看账户信息”尽量复用账户详情，而不是新增多个重复页面。


六、账户分析/健康度

FFJ：

要求账户健康度分析，包括：

账户数量、有效账户、异常账户、账户问题、团队问题、渠道问题等。

账户中心：

已有账户分析，并提出增加更多图表进行分析。

结论：🟡 部分满足。

这里真正需要补的不是页面，而是“健康度规则”。

建议定义统一 Account Health Model，例如：

ACTIVE / IDLE / WARNING / ABNORMAL / DISABLED，并明确什么情况下进入每种状态。

这样 FFJ 的“健康度分析”可以直接从账户中心数据计算。

需要确认：

是否记录 Meta、Google、TikTok 的授权状态、授权时间、失效状态，以及是否支持重新授权。

如果已经支持，则可升级为 ✅。

但不采用FFJ对于TG业务的设计


账户中心材料中没有看到对应能力。


对，这样会比“AI 猜对方有没有接单”可靠很多。这里应该把“是否接单”和“接单后的交付内容识别”拆成两套机制：

前半段用按钮和状态机保证确定性；后半段才使用 AI 解析账户信息。

我建议把这个方案直接定义成「TG Bot 自动下户工作流」。

核心流程可以是：

系统创建需求 → Bot 发询单卡片 → 对方【确认接单 / 拒绝接单】→ 确认后进入等待交付 → 对方 Bot/人员发送账户信息 → AI 解析 → 系统校验 → 人工确认 → 账户入池。

这样整个链路会稳定很多。

一、询单阶段不要让 AI 判断“有没有货”

系统产生 Order，例如：

订单：FFJ-20260917-001
平台：Meta
数量：7
时区：UTC+7
类型：外接
需求：加白
产品：WJ-3

Bot 发到指定供应商 TG 群，并附两个 Telegram Inline Buttons：

[ 确认接单 ] [ 拒绝接单 ]

供应商必须通过按钮给出明确结果。

点击“确认接单”后，Bot 不只是回复一句话，而是后台执行：

Order Status：
WAITING_CONFIRM → ACCEPTED

同时记录：

Accepted By
Accepted At
Telegram User ID
Telegram Group ID
Telegram Message ID

然后原消息的按钮建议变为：

✅ 已接单 · 15:31

这样其他人不会重复点击。

如果点击“拒绝接单”：

WAITING_CONFIRM → REJECTED

并让对方选择一个简单原因，例如：

[ 暂时无货 ]
[ 数量不足 ]
[ 规格无法满足 ]
[ 暂停下户 ]
[ 其他 ]

这个拒绝原因其实非常有数据价值。以后系统可以统计哪个渠道什么产品/时区的接单率最高。

二、还要处理“对方一直不点”

这是一个很重要的异常。

例如询单发出 10 分钟无人响应：

WAITING_CONFIRM
↓
5 min 提醒
↓
10 min TIMEOUT

系统可以自动通知内部运营：

“订单 FFJ-001，DUDU 超过 10 分钟未确认。”

甚至后期可以自动询问第二供应商。

例如：

DUDU → 10 min 未响应
↓
Peak → 自动询单
↓
Peak 点击确认
↓
停止向其他渠道询问

但这个可以作为第二阶段，第一版先做到超时提醒即可。

三、确认以后才进入“等待交付”

供应商点击：

【确认接单】

Bot 回复：

“✅ 已确认接单
订单：FFJ-20260917-001
需求：7 个
等待下户结果。”

系统：

ACCEPTED → PROCESSING

从这一刻开始，AI 才需要参与。

因为 AI 不需要判断“对方到底接没接”，只需要解决一个问题：

“接下来发来的内容里面，哪些是这个订单的交付数据？”

这会大幅降低 AI 的误判概率。

四、我建议要求对方 Bot 回复订单消息

这个设计非常关键。

不要让供应商 Bot 随便在群里发一条结果，让 AI 根据上下文猜是哪个订单。

最好规定：

交付 Bot 必须 Reply 原询单消息。

这样 Telegram 自己就形成：

FFJ Order Message ID: 9281
↑
Supplier Delivery Message Reply To: 9281

系统可以 100% 确定：

这批账户属于 FFJ-20260917-001。

AI 只负责解析内容，不负责订单归属。

这是整个方案稳定性的关键之一。

五、收到结果后再让 AI Parser 工作

例如供应商 Bot 回复：

“开户申请 - 部分完成
下户ID：827
平台：Facebook
账户数：7
已下户：4

XXX (123...)
XXX (456...)
XXX (789...)
XXX (012...)

BM：
xxxx
xxxx”

后台：

Telegram Webhook
→ Order Matcher
→ Parser
→ AI Parser
→ Validator
→ Pending Import

最终产生结构化结果：

Order：FFJ-001
需求：7
本次交付：4
累计交付：4
剩余：3
Account IDs：4
BM IDs：2
解析置信度：98%

系统状态：

PROCESSING → PARTIAL_DELIVERED

Bot 可以自动回复：

“✅ 已识别 4 个账户
订单进度：4 / 7
剩余：3”

这样双方都知道当前进度。

六、“部分交付”必须是一等业务状态

你第二张截图已经证明这个场景是真实存在的。

所以订单状态不能只有：

接单 → 完成。

建议至少设计：

PENDING_CONFIRM
ACCEPTED
REJECTED
TIMEOUT
PROCESSING
PARTIAL_DELIVERED
DELIVERED
PARSING_EXCEPTION
QUANTITY_EXCEPTION
CANCELLED

例如需要 50 个，对方：

第一次给 35
→ 35/50

第二次给 10
→ 45/50

第三次给 5
→ 50/50

系统才自动：

DELIVERED。

七、还需要考虑“确认接单以后又没货”

按钮只能证明“当时愿意接”，不能证明一定能完成。

现实中还可能发生：

确认接单 → 做了一半 → 剩下没货。

所以建议增加一个：

【无法继续交付】

供应商点击后：

当前交付：4/7
未交付：3

选择原因：

“库存不足”

系统：

PARTIAL_DELIVERED → PARTIAL_CLOSED

已经交付的 4 个正常进入后续流程，剩下 3 个重新进入待分配/待询单。

系统甚至可以自动创建：

补单需求：3 个
来源：FFJ-001
原因：供应商库存不足

然后换供应商继续询。


八、异常解析不要自动污染账户池

还有一层是 AI 异常。

例如 AI 从消息里识别：

对方说交付 7 个
但只找到了 6 个 Account ID。

系统不能因为 AI 输出了结果就直接入库。

Validator 应该发现：

Expected Delivery：7
Parsed Account：6

→ QUANTITY_EXCEPTION

进入人工审核。

其他应该自动检查的异常还包括：

Account ID 已存在、Account ID 格式异常、平台不匹配、BM 缺失、重复账户、订单数量超额、时区不一致、渠道不一致等。

所以这里应该坚持：

AI = 理解信息
规则引擎 = 判断信息是否合法

不要让 AI 同时承担两件事情。

十、这个设计还能积累“渠道履约数据”

这是一个额外但很有价值的结果。

既然所有询单都通过 Bot，那么以后每个代理天然就有：

询单次数
接单次数
拒绝次数
接单率
平均响应时间
平均下户时间
完整交付率
部分交付率
异常账户率
订单取消率

例如：

DUDU
接单率：91%
平均响应：2m 13s
平均交付：18m
完整交付：94%
账户异常：1.7%

这正好可以反哺 FFJ 原本想做的“渠道评分”。

甚至以后算法在选择询问哪个供应商时，都可以利用这些数据：

需求 UTC+7 + Meta + 外接
→ 系统根据历史履约能力推荐 DUDU
→ 自动发送询单
→ DUDU 拒绝
→ 自动询问 Peak
→ Peak 接单
→ 等待交付。

这样“渠道评分”就不是产品经理人工定义的一张排行榜，而是由真实订单履约数据产生。


因此你提出的【确认】【拒绝】实际上很关键。它把整个方案从“监听 TG + AI 抽取聊天内容”升级成了真正的“订单协议”。

Bot 负责确定性流程；
Telegram 负责双方交互；
AI 负责非结构化内容理解；
Validator 负责数据正确性；
账户中心负责最终账户资产。

这套逻辑我建议直接写进刚才的需求文档，并把原来的「TG 群组」整个需求替换成「TG Bot 智能询单、履约与自动入库中心」。这样后面研发拿到的就不是一个模糊的“做个 TG Bot”，而是一套可以实现的状态机和业务流程。

结论：🔴 明确 Gap。

如果 TG 是实际运营强依赖渠道，则应保留；如果只是 FFJ 原型阶段提出但实际团队不用，需要重新确认优先级。

三十五、最终覆盖结果

重新纳入“登记打款”后，我会将 FFJ 需求分成三层。

第一层：当前账户中心已经可以直接承接的核心能力。

运营总览、账户中心、账户详情、高级筛选、登记打款、账户池、团队申请账户、人工分配、算法推荐、账户转移、账户回收、更换产品、更换户管、批量账户操作、团队中心、账户分析、预警待办、系统管理。

这一层不建议重复开发。

第二层：已经有数据和基础功能，只需要补规则/字段/分析视图。

账户健康度、API 授权状态、长期未消耗账户、已分配闲置账户、渠道详细分析、团队综合分析、渠道档案、团队档案、账户迁移历史、渠道资金余额分析。

这一层属于“完善现有账户中心”。

第三层：当前方案真正值得新增或重点确认的能力。

1. 账单自动核对及差额处理
2. 渠道/代理评分体系及评分规则
3. Excel 批量导入账户
4. 缺失 Account ID 数据治理
5. 团队批量导入
6. Google Sheets / WPS 在线数据同步
7. Telegram 群组/关键词/自动化规则


三十六、建议最终产品架构

不建议最终菜单照搬 FFJ PDF。

更建议在当前账户中心方案基础上收敛成：

运营总览
→ 账户中心
→ 账户池 / 分配
→ 渠道与资金
→ 团队中心
→ 数据分析
→ 预警与待办
→ 账单核对
→ 数据同步 / TG 自动化
→ 系统管理

其中“账户”仍然作为核心业务对象。

账户所有生命周期动作：

创建/导入 → 入池 → 申请 → 推荐 → 分配 → 使用 → 监控 → 异常 → 转移 → 回收 → 再分配

尽量全部围绕 Account ID 留下完整操作记录。


三十七、最终结论

基于目前两份 PDF 以及补充的“登记打款”功能，不建议得出“账户中心不满足 FFJ”的结论。

更准确的项目结论是：

“现有账户中心已基本覆盖 FFJ 工作台的核心账户运营和管理流程，可作为 FFJ 工作台的主体方案继续建设，无需重新开发另一套工作台。后续工作重点应从页面复制转为补齐 FFJ 特有的账单核对、渠道评分、批量数据治理、外部表格同步及 Telegram 自动化能力，并对账户健康度、闲置账户、渠道资金等统计规则进行统一定义。”

产品评审时，建议把“FFJ.pdf”定位为业务需求参考，把“账户中心.pdf”定位为最终产品架构基础。

这样研发不会产生“FFJ 一套页面 + 账户中心又一套页面”的重复建设问题。
