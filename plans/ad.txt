# 📑 跨平台广告数据接入与权限隔离整改方案

**文档版本：** v1.0  
**适用场景：** 多租户/多团队 SaaS 平台、代理商数据大盘、AI 投流分析系统

## 二、 整体架构整改原则（方法论）

为了支持未来扩展（如接入更多媒体）及为 AI 提供干净的数据，整改必须遵循 **“三层分离”** 原则：

```text
┌─────────────────────────────────────────────────────────────────┐
│ [第一层：平台配置层] (仅超级管理员可见)                             │
│ 作用：全局配置 Meta App ID / Secret, Google Developer Token 等    │
└────────────────────────────────────────┬────────────────────────┘
                                         ▼
┌─────────────────────────────────────────────────────────────────┐
│ [第二层：业务授权层] (团队主管/队员使用)                           │
│ 作用：用户点击 -> OAuth 登录 -> 勾选账户 -> 指定归属团队与负责人    │
└────────────────────────────────────────┬────────────────────────┘
                                         ▼
┌─────────────────────────────────────────────────────────────────┐
│ [第三层：数据权限层] (系统后台自动化处理)                           │
│ 作用：定时拉取数据，根据 RBAC 规则在数据库层面做 SQL 隔离          │
└─────────────────────────────────────────────────────────────────┘
```

## 三、 模块一：数据接入流程 UI/UX 重构（用户侧）

彻底废除现有的“新增字段”、“账户映射”表单。将数据接入简化为 **“3步极简弹窗”**：

### 1. 接入交互流程（以 Meta 为例）

*   **Step 1：选择媒体**
    *   页面呈现 Meta, Google, TikTok, Snapchat 图标。用户点击 `[+ 绑定 Meta 账户]`。
*   **Step 2：唤起第三方 OAuth 登录（重定向）**
    *   系统调用 API 唤起 Facebook 官方授权弹窗。
    *   用户在 Facebook 页面登录并同意授权（申请 `ads_read`, `read_insights` 权限）。
*   **Step 3：账户导入与归因分配（核心页面）**
    *   授权成功后，后端根据返回的 Token 自动调 API 获取该账号下的所有广告账户，并在前端列表展示，供用户勾选：

> **检测到当前 FB 账号包含以下广告账户，请配置导入规则：**
> 
> | 勾选 | 广告账户名称 / ID | 默认分配团队 | 默认负责人 (成员) | 户管 (主管) |
> | :--- | :--- | :--- | :--- | :--- |
> | [x] | 服装站_FB_01 (`act_100001`) | [ Team A 🔻 ] | [ 王五 🔻 ] | [ 李四 (自动填充) ] |
> | [x] | 服装站_FB_02 (`act_200001`) | [ Team A 🔻 ] | [ 张三 🔻 ] | [ 李四 (自动填充) ] |
> | [ ] | 个人测试户 (`act_999999`) | -- *(不导入)* | -- | -- |
>
> `[ 确认导入并开启数据同步 ]`

## 四、 模块二：多租户与数据 RBAC 权限模型设计（核心）

针对“**团队主管看全队，队员看自己+分配的**”需求，后端必须实现**行级数据权限控制（Row-Level Security）**。

### 1. 实体关系图（ER Diagram）

```text
[ Tenant 租户 ]
   └── [ Team 团队 ] (如: Team A)
        ├── [ User 用户 ] (如: 李四-主管, 张三-队员)
        └── [ Ad Account 广告账户 ] (如: act_100001)
             ├── 属性: owner_user_id (接入人/主负责人)
             ├── 属性: manager_user_id (户管/主管)
             └── 交叉表: account_permissions (额外共享给哪些 User)
```

### 2. 角色与数据可见性矩阵（Visibility Matrix）

| 系统角色 | 账户列表 (账户中心) 可见范围 | 报表数据 (Dashboard/AI) 可见范围 |
| :--- | :--- | :--- |
| **超级管理员** | 全公司所有团队的所有账户 | 全公司所有数据 |
| **团队主管 (Manager)** | **本团队 (Team)** 内所有人接入及分配的所有账户 | 本团队所有账户的展示、消耗、ROI 等数据 |
| **普通队员 (Member)** | 满足以下任一条件：<br>1. 自己通过 OAuth 接入的账户 (`owner_user_id == Self`)<br>2. 被主管显式分配给自己的账户 (`Shared_User_ID == Self`) | 仅能查看自己拥有/被分配账户的报表数据 |

### 3. 后端 SQL 过滤逻辑规范（开发必看）

当任何用户请求“账户列表”或“Dashboard 数据”时，后端 API 必须在中台增加统一的 **Data Filter 中间件**，SQL 伪代码如下：

```sql
SELECT * FROM ad_accounts 
WHERE 
   -- 情况1：超级管理员，无限制
   (:user_role = 'SUPER_ADMIN') 
   
   -- 情况2：团队主管，按 Team ID 隔离
   OR (:user_role = 'TEAM_MANAGER' AND team_id = :current_user_team_id) 
   
   -- 情况3：普通队员，看自己Owner的 OR 被共享的
   OR (:user_role = 'TEAM_MEMBER' AND (
        owner_user_id = :current_user_id 
        OR id IN (SELECT account_id FROM account_shares WHERE user_id = :current_user_id)
      ));
```

## 五、 模块三：后台数据 Pipeline 与自动同步引擎整改

既然只做“数据读取与 Dashboard 展现”，后端必须构建自动化的 ETL 数据管道：

```text
[ 平台 Token 续期 Worker ] ──> [ 账户元数据同步 (Discovery) ] ──> [ 报表流水同步 (Insights) ] ──> [ 数据清洗与归一化 ] ──> [ ClickHouse/PostgreSQL ]
```

### 1. 字段标准化定义 (Unified Schema)
后端需要把 Meta, Google, TikTok 返回的异构字段统一映射为标准表结构，**禁止在前端做映射**：

```sql
CREATE TABLE fact_daily_ad_report (
    stat_date Date,                 -- 统计日期
    tenant_id String,               -- 租户 ID
    team_id String,                 -- 团队 ID
    owner_user_id String,           -- 接入人 ID
    platform String,                -- 媒体 ("meta", "google", "tiktok")
    account_id String,              -- 广告账户 ID
    spend Decimal(18,4),            -- 消耗 (已统一转换为账号原币种或 USD)
    impressions Int64,              -- 展示数
    clicks Int64,                   -- 点击数
    conversions Int64,              -- 转化数
    updated_at DateTime             -- 数据最后更新时间
);
```

### 2. 增量同步与归因窗口回溯机制
*   **频次：** 每 4 小时轮询拉取一次“当天”的数据（用于 Dashboard 准实时显示）。
*   **重叠拉取（重要）：** 每天凌晨 2:00，强制拉取**过去 7 天**的数据。
    *   *原因：* 广告平台（尤其是 Meta iOS14+ 归因）存在数据延迟与回溯，必须覆盖重写过去 7 天的数据，保证 AI 分析的数据精准度。

## 六、 模块四：前端“账户中心”数据对齐

针对你提供的 **截图 8（账户中心）**，前端字段与后端数据源的绑定映射关系如下：

```text
截图中的 UI 字段                             对应后端数据库字段 / 逻辑来源
┌───────────────────────┐                  ┌──────────────────────────────────────────────┐
│ 账户 ID (act_100001)   │ ───────────────> │ ad_accounts.account_id                       │
│ 媒体 (Meta/Google)    │ ───────────────> │ ad_accounts.platform                         │
│ 归属/团队 (Team B)     │ ───────────────> │ teams.team_name                              │
│ 成员 (赵磊)           │ ───────────────> │ users.display_name (WHERE id = owner_user_id)│
│ 户管 (陈明)           │ ───────────────> │ users.display_name (WHERE id = manager_id)   │
│ 资产状态 (使用中/闲置) │ ───────────────> │ 系统内部定义逻辑 (如有流水则为使用中)           │
│ 媒体状态 (正常/封禁)   │ ───────────────> │ API 实时/同步返回的账户状态 (ACTIVE/DISABLED) │
│ 已花费 (Spend)        │ ───────────────> │ SUM(fact_daily_ad_report.spend)              │
│ 剩余额度 (Balance)    │ ───────────────> │ ad_accounts.balance (由 Discovery API 拉取)  │
└───────────────────────┘                  └──────────────────────────────────────────────┘
```

**界面交互补全建议：**
*   在列表顶部增加 **“资产分配”** 按钮：主管勾选某个账户，点击“资产分配”，可以把该账户共享给团队内的其他“队员 B”查看。

## 七、 研发实施路线图（Roadmap）

建议分 3 个迭代（Sprint）推进整改：

```text
迭代 1 (Sprint 1): 权限与数据模型重构 [后端重点]
  ├── 1.1 建立 Tenant / Team / User / Account 数据库关系表
  ├── 1.2 在 API 层注入数据 RBAC 行级过滤中间件
  └── 1.3 废除前端 Connector/ACCOUNT_MAP 等代码级配置页面

迭代 2 (Sprint 2): 真实 OAuth 流程与账户导入 [前后端同步]
  ├── 2.1 对接 Meta / Google / TikTok 官方 OAuth 授权回调
  ├── 2.2 实现“点击授权 -> 拉取账户 -> 勾选分配团队与成员”前端弹窗
  └── 2.3 完成 Token 自动续期 Worker

迭代 3 (Sprint 3): 报表 Pipeline 与账户中心对齐 [业务闭环]
  ├── 3.1 实现每日增量数据拉取与统一 Schema 入库 (ClickHouse/MySQL)
  ├── 3.2 将清洗后的数据对齐至“账户中心”列表 (如截图8)
  └── 3.3 为 Dashboard 及 AI 分析模块提供统一的 Data API
```
